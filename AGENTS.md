# AGENTS.md — SpaceBattle

Инструкция для разработчиков и ИИ-агентов, работающих с репозиторием. Подробная документация лежит в `docs/` (начинайте с `docs/README.md`).

Если описание расходится с кодом, правильным считается код.

## О проекте

SpaceBattle — игровой сервер для сетевой игры «Космический бой» на **C# / .NET 10**.
Ключевые идеи:

- любое действие в игре — **команда** (`ICommand.Execute()`);
- зависимости получают из собственного **IoC-контейнера со скоупами** (`Ioc.Resolve`);
- адаптеры к интерфейсам игровых объектов (`IMoving` и др.) **генерируются во время выполнения** (Roslyn);
- действия игроков собираются из **конфигурации** (`Config/*.config`);
- игры идут на **серверных потоках**, поток для игры выбирает **кольцо консистентного хэширования**;
- сервер умеет снимки игр (JSON), перенос игр между серверами, перераспределение игр между потоками, JWT-авторизацию и HTTP API.

Состав каждой ветки отличается: в одних есть серверный стек, в других — игровые команды. Что где лежит, написано в `docs/01-branches.md`.

## Правила работы

- Не коммитить, не пушить и не переключать ветки без явной просьбы пользователя. Сборку, тесты и эксперименты выполнять в отдельной копии репозитория.
- Недостающие требования уточнять у пользователя, а не выдумывать.
- Любое утверждение «тесты проходят» подкреплять свежим запуском `dotnet test` (с английским выводом: `DOTNET_CLI_UI_LANGUAGE=en VSLANG=1033`).
- Общаться с пользователем по-русски.
- Код, написанный другим участником, менять только по согласованию с ним.

## Правила кода

Первые две проверяются автотестом `ArchitectureConstraintsTests` и ломают сборку PR.

1. В `SpaceBattle.Lib` **нет `for` и `while`**. Можно `foreach`, LINQ и рекурсию.
2. В папках `Commands`, `ValueObjects`, `Threads`, `Receivers`, `Processors`, `Behaviours`, `Queues` **нет обращений к `Ioc`**. Зависимости приходят через конструктор (интерфейсы или `Func<>`). С контейнером работают `Registration/RegisterIoCDependency*`.
3. Новое поведение добавляется **новым классом и регистрацией**, а не правкой старого (SOLID: открытость/закрытость, разделение интерфейсов).
4. Объекты создаются в стратегиях IoC и фабриках. В регистрациях, стратегиях и при создании исключений `new` допустим.
5. Конструкторы проверяют аргументы (`ArgumentNullException.ThrowIfNull` и т. п.).
6. **Два `ICommand`**: `App.ICommand` (из `core.dll`, только для самого IoC, пишется с префиксом) и `SpaceBattle.Lib.ICommand` (все игровые команды). Не путать.
7. `core.dll` и `scopes.dll` не менять.

### Тесты

8. xUnit. Имя теста описывает сценарий: `Что_Происходит_При_Каком_Условии`.
9. В тестах не блокируют задачи (`.Wait()`, `.Result`, `Task.WaitAll`) — используйте `async Task` и `await task.WaitAsync(timeout)` (иначе предупреждение xUnit1031).
10. Текущая область IoC хранится отдельно для каждого потока (`ThreadLocal`). После `await` код может продолжиться на другом потоке, поэтому обращения к `Ioc` делают до `await` или внутри нужной области (`ScopeExecution.InScope`).
11. Покрытие тестами каждого изменения — выше 90 %.

### Git и pull request

12. Сообщения коммитов — **Conventional Commits**: `feat(server): ...`, `fix(routing): ...`, `test(game-runner): ...`, `refactor(...)`.
13. В дифф PR не должно попадать удалённых строк: PR только добавляет код. Правка кода из этого же PR вносится в тот коммит, где код появился (`fixup` + `rebase -i --autosquash`).
14. PR выстраиваются **стеком**: каждая ветка основана на предыдущей. После изменения нижней ветки верхние перебазируются: `git rebase --onto <новая-основа> <старая-основа> <ветка>`, затем `git push --force-with-lease`.
15. Слияние стека — снизу вверх, merge-коммитом или rebase-merge (не squash), после каждого слияния базу следующего PR меняют на `main`.

## Как устроено — в двух абзацах

Сообщение игрока `{gameId, command, args}` приходит по HTTP (`POST /messages`, заголовок `Authorization: Bearer <JWT>`), проходит проверку токена, белый список команд и права игрока, попадает в очередь серверного потока и выполняется как команда `Messages.Command.<имя>` внутри IoC-скоупа своей игры. Игра — это очередь команд с квантом времени; одна игра выполняется на одном потоке.

Сервер (`Server`) управляет потоками и кольцом хэширования. Его состояния (`Created`, `Running`, `Closed`) — отдельные классы в `Servers/States/`; интерфейс разделён на `IServerLifecycle`, `IServerThreads`, `IServerAvailability`. Остальное — в `docs/02-architecture.md`.

## Перед отправкой изменений

- Сборка без предупреждений, все тесты зелёные.
- Нет `for`/`while` и обращений к `Ioc` в предметных папках.
- В диффе нет удалённых строк.
- Коммиты соответствуют Conventional Commits.
- Если менялась нижняя ветка стека, перебазированы все верхние.
